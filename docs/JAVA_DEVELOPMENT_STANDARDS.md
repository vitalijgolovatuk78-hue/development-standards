# Стандарт Java-розробки

**Статус:** базовий стандарт проєктів  
**Профіль:** сучасна Java, збалансована архітектура, помірно суворі правила  
**Мова документа:** українська  
**Застосування:** усі Java-проєкти, якщо конкретний проєкт не визначає обґрунтовані винятки.

Цей документ доповнює [загальні стандарти написання коду](CODE_WRITING_STANDARDS.md). Якщо правила перетинаються, діють обидва документи. Безпека, коректність і підтримуваність мають пріоритет над зручністю або швидкістю реалізації.

## 1. Базові принципи

1. Використовувати сучасну підтримувану версію Java. Java 17, 21 і 25 є орієнтирами LTS-релізів, але конкретну версію обирати з урахуванням підтримки Spring Boot, бібліотек, середовища розгортання та вимог проєкту.
2. Не оновлювати Java, Spring Boot або інші залежності лише заради номера версії. Оцінювати сумісність, виправлення безпеки, строк підтримки та вартість міграції.
3. Для нових проєктів за замовчуванням розглядати Maven або Gradle; обирати один інструмент і дотримуватися його послідовно.
4. Керувати версіями залежностей централізовано: Spring Boot dependency management/BOM або узгоджені механізми Maven/Gradle. Не задавати версії однієї й тієї самої залежності в різних місцях без причини.
5. Не додавати бібліотеку, якщо задачу можна надійно вирішити стандартними засобами Java або вже наявними залежностями.
6. Використовувати UTF-8, узгоджений формат файлів і автоматичне форматування/перевірку стилю, якщо це налаштовано в проєкті.
7. Публічні API, складні алгоритми та нетривіальні бізнес-правила документувати. Не коментувати кожен очевидний рядок.

## 2. Мова Java та стиль коду

### 2.1 Читабельність і типізація

- Дотримуватися стандартних Java naming conventions: `UpperCamelCase` для класів та інтерфейсів, `lowerCamelCase` для методів і змінних, `UPPER_SNAKE_CASE` для констант.
- Давати імена за змістом, а не за типом або короткою абревіатурою. Скорочення використовувати лише загальноприйняті.
- Обмежувати область видимості: починати з найменшого необхідного рівня доступу; не робити поля `public` без чіткої причини.
- Надавати перевагу незмінним даним: `final`, незмінним DTO/об'єктам і локальним змінним, які не перевизначаються.
- Не використовувати raw types та небезпечні unchecked casts без необхідності. Якщо придушення warning неминуче, обмежити його найменшою ділянкою та пояснити причину.
- Не повертати `null` як звичайний результат, якщо можна використати порожню колекцію, явний результат або `Optional`. Не використовувати `Optional` для полів JPA-сутностей чи кожного параметра методу.
- Не зловживати `var`: застосовувати, коли тип очевидний із правої частини та це покращує читабельність.
- Використовувати `record` для простих незмінних носіїв даних, коли це відповідає семантиці та вимогам серіалізації/фреймворку.
- Використовувати `enum` замість наборів магічних рядків або чисел для закритих наборів значень.
- Перевіряти вхідні аргументи на межах методів та компонентів. Інваріанти об'єкта мають бути захищені самим об'єктом.
- Уникати надмірної кількості параметрів. Для складних наборів пов'язаних параметрів розглянути окремий тип параметрів.

### 2.2 Об'єктноорієнтований дизайн

- Клас повинен мати чітку відповідальність і зрозумілу причину для зміни.
- Віддавати перевагу композиції перед успадкуванням, якщо немає справжнього відношення «є різновидом».
- Не створювати інтерфейс для кожного класу автоматично. Інтерфейс потрібен для контракту, кількох реалізацій, межі модуля або тестованої залежності.
- Інкапсулювати стан; не відкривати змінні поля назовні.
- Уникати god objects, циклічних залежностей і надмірно глибоких ієрархій.
- Бізнес-логіку не розміщувати в контролерах, конфігураційних класах або JPA-сутностях без обґрунтованої доменної причини.
- Не створювати абстракції «про запас». Спочатку підтвердити повторювану потребу.

### 2.3 Обробка помилок

- Використовувати винятки для помилкових або виняткових ситуацій, а не як звичайний механізм керування потоком.
- Не перехоплювати `Exception` або `Throwable` без конкретної причини. Не ковтати винятки та не залишати порожні `catch`.
- Не перехоплювати виняток лише для того, щоб викинути такий самий без додаткового контексту.
- Створювати власні винятки, коли вони уточнюють доменну або прикладну помилку.
- Зберігати початкову причину через `cause`, коли помилку обгортають.
- Не використовувати повідомлення винятку як стабільний машинний код помилки.
- Не показувати клієнту stack trace, SQL, внутрішні шляхи, секрети або технічні деталі.
- Переривання потоку обробляти коректно: якщо `InterruptedException` не передається далі, відновити interrupt status через `Thread.currentThread().interrupt()`, якщо це відповідає сценарію.

## 3. Архітектура Java-застосунку

### 3.1 Рекомендована базова структура

Для звичайного Spring Boot backend-проєкту використовувати зрозумілий поділ за функціональними областями або модулями. Наприклад:

```text
src/main/java/com/example/app/
  feature/
    user/
      api/             # REST-контролери та HTTP-моделі
      application/     # сценарії використання та координація
      domain/          # бізнес-модель і правила (за потреби)
      infrastructure/  # JPA, зовнішні адаптери (за потреби)
  shared/              # лише справді спільні компоненти
  config/               # конфігурація Spring
src/main/resources/
  application.yml
  db/migration/
src/test/java/
```

Це орієнтир, а не обов'язкова схема для кожного невеликого застосунку. Не створювати порожні шари або пакети, які нічого не додають.

### 3.2 Межі відповідальності

- **Controller:** HTTP-рівень — прийом запиту, валідація формату, виклик прикладного сценарію та формування відповіді. Не містить бізнес-логіки або SQL.
- **Service/Application layer:** реалізує сценарії використання, координує доменну логіку та залежності. Транзакційні межі зазвичай визначаються тут.
- **Domain:** бізнес-правила та інваріанти, незалежні від HTTP, бази даних і конкретного фреймворку, коли складність домену це виправдовує.
- **Repository:** абстракція доступу до даних або Spring Data repository. Не переносити сюди правила HTTP чи форматування відповідей.
- **Infrastructure:** реалізації доступу до БД, зовнішніх сервісів, черг, файлових систем та інших технічних інтеграцій.
- **DTO:** моделі передачі даних між межами системи. Не повертати JPA entity безпосередньо з REST API.

### 3.3 Архітектурний баланс

- Для простого CRUD достатньо контролера, сервісу, repository та DTO; не вводити складну Clean/Hexagonal Architecture без потреби.
- Для складного домену, кількох інтеграцій або незалежних адаптерів розглянути модульну чи Hexagonal Architecture.
- Починати з модульного моноліту, якщо немає доведених причин для мікросервісів.
- Модулі повинні мати явні межі та мінімізувати доступ до внутрішніх деталей один одного.
- Не створювати універсальний `BaseService`, `BaseController` або generic repository лише для скорочення кількох рядків.
- Залежності мають бути спрямовані до стабільніших контрактів; уникати циклів між модулями.
- Рішення про кеш, черги, мікросервіси, CQRS або event sourcing приймати лише після аналізу вимог і компромісів.

## 4. Spring Boot та Spring Framework

### 4.1 Dependency Injection та компоненти

- Використовувати constructor injection як стандартний спосіб впровадження залежностей.
- Не використовувати field injection через `@Autowired` без виняткової технічної причини.
- Не створювати вручну об'єкти, якими має керувати Spring, якщо вони повинні брати участь у DI та життєвому циклі контейнера.
- Не позначати кожен клас `@Component` автоматично. Використовувати відповідну роль: `@Service`, `@Repository`, `@Controller` тощо, коли це додає семантику.
- Уникати service locator та глобального доступу до ApplicationContext.
- Не допускати циклічних залежностей між Spring beans; виправляти структуру відповідальностей, а не маскувати проблему.

### 4.2 Конфігурація

- Зовнішні налаштування зберігати в конфігурації та змінних середовища, а не в коді.
- Для згрупованих налаштувань використовувати типізовані `@ConfigurationProperties` з валідацією, а не розростання `@Value` по всьому коду.
- Розділяти конфігурації за середовищами лише там, де відрізняються параметри; не дублювати цілі файли без потреби.
- Не комітити паролі, токени, приватні ключі та production credentials. Для локальної розробки використовувати приклади без секретів; для production — secret manager або захищені змінні середовища.
- Невалідна критична конфігурація має зупиняти запуск із зрозумілим повідомленням.
- Не вимикати стандартні механізми безпеки або валідації заради швидкого запуску.

### 4.3 Транзакції

- Визначати транзакції на межі прикладного сценарію, зазвичай у service/application layer.
- Використовувати `@Transactional` усвідомлено: розуміти propagation, isolation, readOnly та правила rollback.
- Тримати транзакції короткими; не виконувати в них повільні HTTP-виклики, очікування користувача або тривалі обчислення.
- Пам'ятати про proxy semantics Spring: self-invocation може не проходити через transactional proxy.
- Не вважати `readOnly = true` універсальним захистом від запису.
- Для операцій між БД і зовнішньою системою не покладатися на одну локальну транзакцію. Розглянути outbox, ідемпотентність або компенсаційні дії, якщо потрібна узгодженість.
- Не приховувати помилку всередині транзакції, якщо це може призвести до commit некоректного стану.

### 4.4 Валідація та обробка помилок

- Використовувати Bean Validation (`@Valid`, `@Validated`, constraint annotations) для перевірки вхідних даних на межі.
- Бізнес-інваріанти перевіряти також у прикладному або доменному шарі; HTTP-валідація не замінює бізнес-перевірки.
- Централізувати HTTP error mapping через `@ControllerAdvice` / `@RestControllerAdvice`.
- Повертати стабільну структуру помилки з кодом, безпечним повідомленням та, за потреби, деталями полів.
- Використовувати узгоджений формат, наприклад Problem Details (RFC 9457), якщо він підходить API.
- Не повертати клієнту внутрішній stack trace або текст SQL.

### 4.5 Production readiness

- Для сервісів, яким потрібен моніторинг, розглянути Spring Boot Actuator та Micrometer.
- Відкривати лише необхідні management endpoints; захищати їх окремо та не публікувати чутливі дані.
- Налаштовувати health checks, метрики та кореляцію логів/трас відповідно до середовища.
- Не вмикати debug-режими та детальне логування секретних даних у production.
- Перевіряти поведінку застосунку під час graceful shutdown, втрати БД та недоступності зовнішніх сервісів.

## 5. SQL, PostgreSQL, JPA та Hibernate

### 5.1 Модель даних і SQL

- Проєктувати схему від бізнес-вимог: сутності, зв'язки, обмеження, унікальність та правила видалення.
- Використовувати правильні типи даних, `NOT NULL`, `UNIQUE`, `CHECK` та foreign keys там, де вони захищають цілісність.
- Додавати індекси під реальні запити та профілі навантаження, а не на кожну колонку.
- Перевіряти плани виконання повільних запитів через інструменти СУБД (наприклад, `EXPLAIN ANALYZE` у PostgreSQL).
- Використовувати параметризовані запити. Ніколи не конкатенувати користувацьке введення в SQL.
- Уникати `SELECT *` у критичних або великих запитах; вибирати потрібні колонки.
- Пагінацію та сортування робити на стороні БД. Поля сортування, які не можна bind-параметризувати, вибирати лише з allowlist.
- Враховувати часові пояси: зберігати моменти часу в узгодженому форматі (зазвичай UTC/instant), а локальний часовий пояс визначати на межі відображення.
- Гроші зберігати в точному десятковому типі або в цілих найменших одиницях; не використовувати `float`/`double` для фінансової арифметики.

### 5.2 JPA/Hibernate

- JPA entity — це модель persistence, а не DTO для зовнішнього API.
- Обережно проєктувати `equals()` та `hashCode()` для entity з урахуванням ідентичності та життєвого циклу ID; не включати змінні колекції та lazy associations без аналізу.
- Уникати необдуманого `CascadeType.ALL` та `orphanRemoval = true`; каскади мають відповідати реальному володінню життєвим циклом.
- Для зв'язків за замовчуванням віддавати перевагу LAZY, де це підтримується та відповідає вимогам. Не робити всі зв'язки EAGER для «зручності».
- Планувати завантаження даних під конкретний сценарій: fetch join, EntityGraph, DTO projection або batch fetching.
- Перевіряти N+1 запити; не вважати, що ORM автоматично оптимізує будь-який граф об'єктів.
- Не повертати lazy entity за межі транзакції/сесії з розрахунком на випадкову ініціалізацію.
- Уникати масового завантаження великих таблиць у пам'ять. Використовувати pagination, streaming або batch processing з контролем persistence context.
- Для конкурентних змін застосовувати optimistic locking через `@Version`, коли це відповідає моделі конфліктів.
- Не покладатися лише на перевірку в Java для унікальності або цілісності: остаточні гарантії мають бути в БД.
- Не використовувати `ddl-auto=update` як production-стратегію керування схемою.

### 5.3 Міграції та транзакційність даних

- Для керування схемою використовувати Flyway або Liquibase (обрати один інструмент).
- Міграції зберігати в репозиторії, нумерувати/іменувати послідовно та перевіряти в CI.
- Не редагувати вже застосовані production-міграції; створювати наступну міграцію.
- Перевіряти сумісність міграцій із наявними даними та порядком розгортання версій застосунку.
- Для великих таблиць планувати безпечні поетапні зміни, backfill та індексацію з урахуванням блокувань.
- Важливі обмеження й транзакційні гарантії забезпечувати на рівні БД, де це можливо.

## 6. REST API та інтеграції

### 6.1 Проєктування API

- Використовувати послідовні URL, HTTP methods та status codes відповідно до семантики HTTP.
- Розділяти зовнішні API-моделі та внутрішні entity/domain models.
- Для створення ресурсу зазвичай повертати `201 Created` і, за потреби, `Location`; для успішного видалення — відповідний `204 No Content`, якщо тіло не потрібне.
- Не повертати `200 OK` для кожної ситуації незалежно від результату.
- Узгодити формат дат, часових поясів, чисел, ідентифікаторів, помилок і пагінації.
- Валідувати path/query/body parameters та обмежувати розміри запитів.
- Для змін несумісних контрактів використовувати контрольоване версіонування або сумісну еволюцію.
- Документувати API через OpenAPI, якщо API призначене для інших команд, клієнтів або інтеграцій.

### 6.2 Надійність інтеграцій

- Для зовнішніх HTTP-викликів задавати connection/read/response timeouts; не використовувати нескінченне очікування.
- Retry застосовувати лише для тимчасових помилок і лише з обмеженням спроб, backoff та jitter.
- Не повторювати автоматично неідемпотентну операцію без idempotency key або іншого механізму захисту від дублювання.
- Для нестабільних залежностей розглядати circuit breaker, bulkhead та rate limiting, якщо це виправдано.
- Обмежувати розмір відповіді, перевіряти схему та обробляти некоректні відповіді зовнішніх сервісів.
- Не логувати повні токени, персональні дані або чутливі payloads.
- Відокремлювати помилки мережі, помилки протоколу, бізнес-відмови та некоректні дані.

### 6.3 Ідемпотентність і узгодженість

- Для операцій, які можуть повторюватися через retry або повторний запит клієнта, визначити правила ідемпотентності.
- Для подій та повідомлень враховувати повторну доставку; обробники мають бути ідемпотентними або мати дедуплікацію.
- Не обіцяти exactly-once delivery без конкретного механізму та доказу гарантій.
- Для критичних міжсистемних процесів документувати сценарії часткового успіху та відновлення.

## 7. Тестування: JUnit, Mockito та інтеграційні тести

### 7.1 Загальні вимоги

- Тести є частиною готової функціональності, а не необов'язковим доповненням.
- Назва тесту повинна описувати поведінку або умову та очікуваний результат.
- Один тест має перевіряти одну логічну поведінку; кілька assertions допустимі, якщо вони описують один результат.
- Тестувати публічну поведінку та контракти, а не приватну реалізацію.
- Тести мають бути детермінованими, ізольованими та незалежними від порядку запуску.
- Не використовувати реальний production-сервіс, реальні credentials або спільну production-базу в тестах.
- Не покладатися на `Thread.sleep()` для синхронізації тестів, якщо є детерміновані засоби очікування.

### 7.2 Рівні тестування

- **Unit tests:** швидко перевіряють окрему бізнес-логіку без Spring context та реальної інфраструктури.
- **Integration tests:** перевіряють взаємодію компонентів, persistence, транзакції, конфігурацію та інтеграції.
- **Web/API tests:** перевіряють HTTP-контракт, статуси, валідацію та формат помилок.
- **End-to-end tests:** перевіряють критичні сценарії через систему цілком; використовувати вибірково через їхню вартість.
- Для БД та інфраструктури розглянути Testcontainers, якщо потрібна перевірка на реальній технології.
- Не замінювати всі інтеграційні тести моками: моки не перевіряють реальну поведінку БД, транзакцій чи HTTP.

### 7.3 JUnit та Mockito

- Для нових тестів використовувати JUnit Jupiter (JUnit 5+ ecosystem) та актуальну сумісну версію.
- Використовувати зрозумілу структуру Arrange / Act / Assert.
- Застосовувати parameterized tests для наборів вхідних даних, які перевіряють одну поведінку.
- Mockito використовувати для зовнішніх залежностей, а не для кожного об'єкта в тесті.
- Не мокати прості DTO, value objects або сам клас, поведінку якого тестуємо.
- Перевіряти значущі взаємодії лише тоді, коли вони є частиною контракту; не прив'язувати тести до кожного внутрішнього виклику.
- Не використовувати надмірну кількість stubbing та lenient mocks для приховування зайвих залежностей.
- Для перевірки винятків використовувати точні типи та, де важливо, перевіряти зміст безпечного повідомлення/коду.
- Для часу, випадковості та зовнішніх систем використовувати контрольовані абстракції або test fixtures.

### 7.4 Покриття та критерії готовності

- Покриття рядків саме по собі не є доказом якості тестів.
- Пріоритет — важлива бізнес-логіка, граничні випадки, валідація, права доступу, транзакції та сценарії помилок.
- Не писати тести лише для досягнення відсотка coverage.
- Перед завершенням задачі запускати релевантні тести та повну збірку, якщо це доступно.
- Якщо тести не запускалися через відсутність середовища або інструментів, прямо зазначити це.

## 8. Безпека застосунку

### 8.1 Секрети та конфігурація

- Заборонено комітити паролі, API keys, access tokens, приватні ключі, production connection strings та інші секрети.
- Використовувати secret manager або захищені CI/CD secrets для середовищ розгортання.
- Додавати безпечні приклади конфігурації без реальних секретів; перевіряти `.gitignore`.
- У разі витоку секрету негайно відкликати/ротувати його; простого видалення з останнього commit недостатньо.

### 8.2 Автентифікація та авторизація

- Розрізняти автентифікацію (хто користувач) та авторизацію (що йому дозволено).
- Перевіряти права доступу на сервері для кожного захищеного ресурсу та дії.
- Не покладатися на приховування кнопок або перевірки лише на клієнті.
- Дотримуватися принципу найменших привілеїв для користувачів, сервісних акаунтів та БД.
- Паролі не зберігати у відкритому вигляді або оборотним шифруванням; використовувати сучасний password hashing алгоритм, призначений для паролів, із належними параметрами.
- Для сесій, cookies, OAuth2/OIDC або JWT використовувати перевірені бібліотеки та офіційні рекомендації. Не реалізовувати криптографічні протоколи самостійно.
- Перевіряти issuer, audience, signature, expiration та дозволені алгоритми токенів; мати план ротації ключів.
- Захищати критичні операції від CSRF там, де це релевантно для обраної моделі автентифікації.

### 8.3 Вхідні дані та типові вразливості

- Валідувати, нормалізувати та обмежувати вхідні дані за довжиною, типом, форматом і допустимими значеннями.
- Запобігати SQL injection параметризованими запитами та безпечним використанням ORM.
- Запобігати XSS: кодувати вивід відповідно до контексту та не довіряти HTML з користувацьких даних.
- Захищатися від SSRF: обмежувати вихідні адреси/схеми, перевіряти redirects та не дозволяти довільний доступ до внутрішньої мережі.
- Обмежувати розмір файлів, типи та вміст завантажень; не довіряти лише розширенню файлу.
- Не повертати stack traces, секрети, внутрішні ID/дані або деталі інфраструктури у відповідях клієнту.
- Встановлювати rate limits та захист від brute force для чутливих endpoint-ів.
- Не вимикати TLS certificate validation у production.

### 8.4 Залежності та дані

- Перевіряти залежності на відомі вразливості та використовувати підтримувані версії.
- Не додавати бібліотеки з невідомих або недовірених джерел без перевірки.
- Мінімізувати збирання та зберігання персональних даних; визначати строки зберігання й правила видалення.
- Маскувати чутливі поля в логах, трасах, метриках і тестових даних.
- Розглядати загрози для кожного нового зовнішнього endpoint, інтеграції та механізму доступу.

## 9. DevOps, Docker та CI/CD

### 9.1 Відтворювана збірка

- Збірка має бути відтворюваною локально та в CI.
- Зафіксувати версію Java toolchain та узгоджені версії plugin/dependency management.
- Використовувати Maven Wrapper або Gradle Wrapper і зберігати wrapper-файли в репозиторії.
- CI має запускати compile/build, тести, статичні перевірки та перевірки залежностей відповідно до розміру проєкту.
- Не ігнорувати помилки збірки або flaky tests без пояснення та плану виправлення.

### 9.2 Docker

- Використовувати офіційні або перевірені базові образи, фіксувати версії; для production за можливості фіксувати digest.
- Використовувати multi-stage builds, щоб не переносити build tools у runtime image без потреби.
- Запускати процес у контейнері від непривілейованого користувача.
- Не вбудовувати секрети у Dockerfile, image layers або build arguments; передавати їх безпечним runtime-механізмом.
- Мінімізувати контекст збірки через `.dockerignore`.
- Не запускати контейнер із зайвими capabilities або root-доступом.
- Визначати health checks, graceful shutdown та коректну передачу сигналів процесу, якщо це потрібно середовищу.
- Контейнер має містити лише необхідні runtime-компоненти.

### 9.3 CI/CD та релізи

- Зберігати pipeline-конфігурацію в репозиторії та перевіряти її зміни.
- Використовувати мінімально необхідні permissions для GitHub Actions та інших CI runners.
- По можливості фіксувати сторонні GitHub Actions на повний commit SHA та регулярно оновлювати їх контрольовано.
- Не друкувати secrets у логах; обмежувати доступ до environments і production deployment.
- Розділяти build, test, package та deploy етапи.
- Виконувати міграції БД контрольовано та з урахуванням сумісності версій.
- Для важливих релізів мати план rollback або roll-forward та перевірку працездатності після розгортання.

## 10. Продуктивність та масштабування

- Спочатку вимірювати, потім оптимізувати. Не робити передчасних micro-optimizations.
- Визначати цільові показники: latency, throughput, error rate, memory/CPU, DB query time.
- Використовувати профілювання, метрики та tracing для пошуку реального вузького місця.
- Контролювати кількість SQL-запитів, N+1, індекси, pagination, connection pool та час транзакцій.
- Обмежувати розмір колекцій, HTTP payloads, upload-и та результати запитів.
- Кешувати лише дані з чіткою стратегією TTL, інвалідації, консистентності та обмеженням пам'яті.
- Не кешувати приватні або користувацькі дані між користувачами без надійної ізоляції ключів.
- Налаштовувати connection pools, thread pools та timeouts відповідно до ресурсів і характеру навантаження.
- Для великих наборів даних використовувати batch/streaming підхід із контрольованим споживанням пам'яті.
- Не збільшувати кількість потоків або розмір пулу навмання: надмірна конкуренція може погіршити продуктивність.

## 11. Багатопотоковість та асинхронність

### 11.1 Безпечна конкурентність

- За замовчуванням віддавати перевагу простому синхронному коду, якщо асинхронність не дає вимірюваної або архітектурної користі.
- Спільний змінний стан мінімізувати; за можливості використовувати immutable objects та message passing.
- Для спільного стану визначати правила синхронізації та видимості пам'яті; не покладатися на випадковий порядок виконання потоків.
- Використовувати високорівневі засоби Java concurrency (`ExecutorService`, concurrent collections, locks, atomics, futures) замість ручного керування потоками без необхідності.
- Не створювати необмежені thread pools або черги.
- Завжди визначати політику завершення, timeout, cancellation та обробки помилок асинхронної задачі.
- Не блокувати event-loop або обмежений пул потоків довгими операціями.
- Уникати deadlocks: не брати блокування у різному порядку та не виконувати зовнішні виклики під lock без потреби.

### 11.2 Virtual threads та reactive

- Для блокувальних I/O сценаріїв розглянути virtual threads, якщо версія Java та всі залежності їх підтримують.
- Virtual threads не роблять CPU-bound обчислення швидшими й не усувають потребу в обмеженні зовнішніх ресурсів (БД, HTTP connections, rate limits).
- Не змішувати reactive stack і blocking calls без чіткого розуміння scheduler/thread model.
- Обирати Spring MVC або WebFlux відповідно до вимог та всієї архітектури, а не через популярність технології.
- Використовувати `CompletableFuture` та інші async API лише з явним executor/контролем ресурсів там, де це важливо.
- Не ігнорувати винятки, які виникають у фонових задачах.

### 11.3 Контекст та транзакції

- Не припускати, що ThreadLocal, security context, MDC або транзакційний контекст автоматично переходять у новий потік.
- Явно передавати або безпечно переносити необхідний контекст у фонові задачі.
- Не використовувати один EntityManager або Hibernate Session одночасно з кількох потоків.
- Не запускати фонову роботу всередині HTTP-запиту без оцінки життєвого циклу, retry, persistence та відновлення після перезапуску.
- Для довготривалих або критичних задач використовувати надійну чергу/сховище задач, якщо втрата роботи при перезапуску неприпустима.

## 12. Логування, спостережуваність та діагностика

- Використовувати logging framework, узгоджений зі Spring Boot; не використовувати `System.out.println` для production-логів.
- Логувати події з корисним контекстом, але не секрети, паролі, токени або повні чутливі payloads.
- Вибирати рівні логування послідовно: ERROR для помилок, які потребують уваги; WARN для підозрілих/відновлюваних ситуацій; INFO для ключових подій; DEBUG для діагностики.
- Не логувати одну й ту саму помилку на кожному шарі без додаткової цінності.
- Додавати correlation/trace ID для зв'язування подій одного запиту або процесу, якщо це підтримує інфраструктура.
- Не використовувати user ID, email або інші висококардинальні/чутливі значення як metric labels.
- Метрики мають відповідати на практичні питання: чи працює сервіс, наскільки він швидкий, де виникають помилки та чи вичерпуються ресурси.

## 13. Документація та підтримка

- README має пояснювати призначення проєкту, вимоги, запуск, конфігурацію, тести та основні команди.
- Описувати змінні середовища та надавати безпечний приклад конфігурації без секретів.
- Документувати API, міграції, інтеграційні контракти та нетривіальні архітектурні рішення.
- Для важливих рішень використовувати короткі ADR (Architecture Decision Records): контекст, рішення, альтернативи та наслідки.
- Після зміни поведінки оновлювати відповідну документацію.
- Не залишати документацію, яка суперечить фактичній поведінці коду.

## 14. Винятки з правил

- Відхилення допустимі, якщо є конкретна технічна причина, обмеження legacy-системи або вимога сумісності.
- Виняток має бути локальним, зрозумілим і задокументованим там, де він може здивувати наступного розробника.
- Не використовувати «так швидше» як єдине обґрунтування для компромісу в безпеці, цілісності даних або тестуванні критичної логіки.
- Для навчальних, експериментальних або короткоживучих прототипів можна спростити частину інфраструктури, але явно позначити межі прототипу та не переносити небезпечні спрощення в production.

## 15. Робочий процес для Java-задачі

1. **Уточнити вимоги:** сценарії, користувачі, дані, обмеження, критерії готовності.
2. **Оглянути репозиторій:** версії Java/Spring, build tool, модулі, стиль, наявні тести та архітектуру.
3. **Дослідити:** перевірити офіційну документацію для актуальних API/версій; для нетривіальних рішень порівняти якісні відкриті реалізації та перевірити їхні ліцензії.
4. **Спроєктувати:** обрати найпростішу архітектуру, визначити межі транзакцій, контракти API, модель даних і ризики.
5. **Реалізувати невеликими кроками:** не змішувати непов'язані зміни; не додавати зайвих залежностей.
6. **Перевірити:** unit/integration/API тести, збірка, статичний аналіз, перевірка залежностей та міграцій відповідно до задачі.
7. **Переглянути:** безпека, права доступу, SQL, N+1, транзакції, логування, ресурси та обробка помилок.
8. **Документувати:** оновити README/API/ADR/конфігураційні приклади, якщо це потрібно.
9. **Підсумувати:** повідомити, що змінено, які команди реально виконано, результати тестів і невирішені обмеження.

## 16. Чекліст перед завершенням задачі

- [ ] Вимоги та критерії готовності виконані.
- [ ] Код відповідає загальним стандартам і цьому Java-стандарту.
- [ ] Архітектура не складніша, ніж потрібно.
- [ ] Немає секретів у коді, конфігурації, логах або commit.
- [ ] Вхідні дані перевіряються, права доступу перевірені.
- [ ] SQL параметризований; міграції контрольовані.
- [ ] Транзакції мають правильні межі; немає очевидного N+1.
- [ ] Обробка помилок не розкриває внутрішні дані.
- [ ] Додані або оновлені релевантні тести.
- [ ] Збірка та перевірки запущені; результати відомі.
- [ ] Документація оновлена, якщо зміни впливають на використання.
- [ ] Відомі компроміси та невиконані перевірки явно описані.
